Task 1 — Move Password Login to Backend
为什么先做：先建立 session infrastructure。SAML 只需要"再加一种签发 session 的方式"，不需要从头搭建。

改动内容：

新增 Backend/auth.py（约 46 行）：SESSIONS dict + POST /api/login + cookie 签名

Frontend/Login.jsx：本地比对逻辑 → 改为 fetch('/api/login')

Task 2 — Enable HTTPS on Backend
为什么先做：太湖 SP metadata 中 ACS URL 为 https://170.106.75.184:8000/saml/acs，但 backend 仅服务 HTTP，太湖回调时会 TLS 握手失败。

改动内容（共约 8 行）：

沿用现有 Backend/cert.pem / key.pem（Subject = CN=170.106.75.184，SAN = IP，有效期至 2027-05-27）

Two Login Paths, One Session
两条路径最终收敛到同一个 HttpOnly cookie：



Path A（Password）:
   Login.jsx → POST /api/login → auth.py 校验 → 签发 cookie，SESSIONS[id] = username
Path B（SAML）:
   Login.jsx → /saml/login → 太湖 SSO → POST /saml/acs → saml.py 校验
       → 签发 cookie，SESSIONS[id] = email
Cookie 属性：HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=28800（有效期 8 小时）

Session 存储
进程内 SESSIONS: dict[str, str]（session_id → user_id email）。Backend 重启后 session 清空，目前频率可接受（因为 /api/* 暂无 middleware 强制校验 cookie）。若 T2 实施后出现频繁掉线，再考虑迁移至 Redis 或改用 signed cookie。

审计日志
backend.log 中每次登录记录一行 INFO:saml:SAML login: user=<email>。完整 attributes 仅在 DEBUG level 输出，不进入 INFO 日志。

Lessons Learned
Documentation-first 确实有效 — 设计文档共约 1300 行，写文档花的时间远少于它节省的返工时间。本次 16 个 commits 每个独立、可读、可 revert，上次的代码混乱没有重演。

拆分增量交付 — 3 个独立任务，每个改动在 200 行以内，每个单独合入 master。任一环节出问题不影响其他部分。

复用已有基础设施 — python3-saml + xmlsec 是上次失败留下的"沉没成本"，本次让它发挥价值。HTTPS 证书同样复用现有资产。

实测，不要假设 — 原本推测属性名为 email / mail / emailAddress，实际是 OID format。通过 dev-only logger.info 捕获一次真实流量，确认后回填代码并降级至 logger.debug。

明确 user_id 的来源 — 基于 token 的系统必须有稳定的用户标识来源。NameID transient 是个常见陷阱，必须使用 attributes 中的 email 或 uid。
